## 决策一：不用浏览器，走隐藏 JSON 接口

**背景**：列表页是 JS 渲染的，第一版用 Playwright 打开渲染，跑完 16 个栏目要 **3 分 40 秒**。

**发现**：抓网络请求后发现列表数据其实来自一个纯 HTTP 的 JSON 后端：

```
GET https://hbj.huzhou.gov.cn/api-gateway/jpaas-publish-server/front/page/build/unit
    ?pageSize=<n>&siteId=...&pageId=...&tagId=zw&unitId=<栏目 colId>
```

**结果**：采集时间 3m40s → **约 30 秒**，CPU 消耗降一个数量级，而且 **Workers 里也能跑**（Workers 不能运行浏览器）。

**代价**：这是个未公开的内部接口，官方改版会让抓取失效。判断依据：`monitor.py` 和 `worker/src/index.js` 各留了独立的解析函数，改版时改一处即可；另外 `worker/src/index.js` 把 `fetchColumn` 等函数都 `export` 了出来，方便用 Node 直接跑单测快速回归。

**附带的坑：tagId**。大部分栏目用 `tagId=zw`，但栏目 `1229858680`（全市建设项目环评信息公示）返回 0 条，要用 `tagId=list` 才有数据。所以两个脚本都维护了 `ALT_TAGS = ('zw','list')` 的回退循环。

## 决策二：Workers Free 的 10ms CPU —— 拆成单元任务

**约束**：官方限制 Workers Free **每次调用 10ms CPU**，而这 10ms **对 HTTP 请求和 Cron Trigger 一视同仁**。「一次请求跑完 16 个栏目」的方案在免费计划上根本不可能，一开始我也因此建议上 Paid——但用户要求必须是免费计划，于是推倒重来。

**方案**：把整条流水线拆成极小的**单元任务**，队列存 KV 的 `pending` 键，cron 每分钟触发一次，每次只消费 1 个任务。

```
scheduled() ──每天一次──▶ startCycle()          # 16 个 list 任务入队
            ──每次调用──▶ runBatch(STEP_SIZE)   # 取 1 个任务执行
```

- `list` 任务：查一个栏目的最新 N 条 → 把未见过的条目转成 `detail` 任务入队
- `detail` 任务：抓一条公告的详情页 → 解析项目表格 → 追加到当月分片

**把 CPU 压进预算的几个手段**：

| 手段 | 效果 |
|---|---|
| 用 `indexOf` 定位边界后切片解析，代替 `String.prototype.matchAll` 全页正则 | 单页解析 **3~12 ms → 0.1~0.23 ms** |
| `STEP_SIZE = 1`（单次调用只做 1 个任务） | 给 `fetch`、KV IO 和冷启动留足余量 |
| KV 按月份分片存储 | 避免每次读写几百 KB 大 JSON 的 CPU |
| `/api/items` 用**字符串拼接**合并月份分片，不 `JSON.parse` 再 `stringify` | 省掉大对象的序列化开销 |
| 看板客户端渲染，Worker 只吐静态外壳 | 服务端彻底不做字符串拼装 |
| 本地用 `process.cpuUsage()` 逐单元实测 | 列表任务 1~3 ms、详情任务 2~4 ms（含 fetch + KV） |

**代价**：首次回灌慢。16 个 list 任务 + 最多 16×12=192 个 detail 任务 ≈ **3~4 小时**才填满。解法是先用本地数据灌种子（`tools/export_kv.py` → `wrangler kv bulk put`），秒变 229 条。另外每个栏目只看最新 12 条（`LIST_LIMIT`），**更老的历史公告 Worker 永远不会补**，历史数据只能靠本地采集后播种。

**写入配额要留意**：KV 免费计划 **1000 次写入/天**。回灌那一轮大约 **400~600 次写入**（每个 detail 任务：写 `pending` + 写月份分片 + 可能写 `idx`），已经接近上限。所以回灌当天不要反复手动打 `/api/start`。

## 决策三：去重不用单独的 seen 键，而是查月份分片

**早期方案**：维护一个 `seen` 键存所有已抓过的 art_id。

**问题**：这个键会随着时间无限膨胀，每次写都要读写整个大对象，既不划算也不安全。

**现在**：数据本来就按月分片存在 `m:<YYYY-MM>` 里，用 `knownIds()` / `hasItem()` 直接查分片。**跨月重复插入**是个真实风险（比如一条 9 月 30 日发布的公告，日期落在相邻的分片里），所以查的不是单个月份而是 `neighborMonths()` 返回的相邻月份集合；detail 任务执行前还会 `hasItem()` **二次确认**，防止队列里的其他任务已经写进去了。

## 决策四：Worker 绝不下载附件本体

**事实**：81 个附件 ≈ **1 GB**，单个最大 **137.5 MB**，常见 20~40 MB。

**三个上限都会爆**：
- Workers 内存 128 MB
- KV 单值上限 25 MB
- KV 命名空间总量 1 GB

**结论**：分工。
- **Worker**：只存元数据 + 附件链接，供看板展示
- **本地 `tools/download.py`**：负责真正下载，支持断点续传、跳过已存在、并发、按单位/关键词/日期/体积过滤

## 决策五：看板的「新增」标记用 fetched_at，不用 localStorage

**早期方案**：前端用 localStorage 记录上次访问时间来判断 NEW。

**问题**：首次加载时 localStorage 是空的，导致「新增」永远显示 0。

**现在**：直接用数据里的 `fetched_at` 字段，落在 **36 小时窗口**内的判定为 NEW。首次加载也能正确显示最新抓到的条目。
