# 01 · 会话全记录

> 从「我想定时看湖州环保环评公示」到全部落地的完整过程，按时间线记录。
> 目的是让未来的会话不用重新踩一遍坑。

## 一、需求提出

用户要求：定时看**湖州市生态环境局的环评公示**。通过澄清确认了三个维度：

| 问题 | 用户选择 |
|---|---|
| 多久看一次 | 工作日每天早上 |
| 产出什么 | 生成 HTML 看板 |
| 关注范围 | 湖州全市，全类型 |

最初尝试用 WorkBuddy 的自动化定时任务承载，但因为后续要上云 + 要下载附件，最终被 Workers 的原生 cron 取代。

## 二、从「能跑起来」到「能上云」

### 阶段 1：本地 Python 采集器（Playwright 版 → 240 秒）

第一版 `monitor.py` 用 Playwright 打开列表页渲染 JS，跑完 16 个栏目要 **3 分 40 秒**。这在本地勉强能忍，但意味着 **Cloudflare Worker 里根本没法跑**（Workers 不能开浏览器）。

### 阶段 2：发现隐藏 JSON 接口（→ 30 秒）

用 DevTools 抓网络请求，发现列表页虽然是 JS 渲染的，但背后有一个**纯 HTTP 的 JSON 后端**：

```
GET /api-gateway/jpaas-publish-server/front/page/build/unit?...
```

直接请求这个接口就能拿到栏目列表 JSON，**浏览器依赖彻底去掉**。本地采集从 3m40s 降到 **约 30 秒**，Worker 部署也变得可行。这是整个项目最关键的一次转折——详见 [`02-技术决策.md`](02-技术决策.md)。

### 阶段 3：部署到 Cloudflare Workers + KV

用户要求部署到 Workers 并把结果存 KV。当时的设计是「一次 cron 跑完整个采集流程」，这在付费计划上没问题。

## 三、转折点：「我一定要用免费的」

用户明确要求只用免费计划。我一开始判断「免费计划基本不可能跑完」，建议上 Paid——**这个判断被用户推翻了**。重新查了官方文档后确认：

| Workers Free 限制 | 数值 |
|---|---|
| CPU 时间（**HTTP 请求和 Cron Trigger 都一样**） | **10 ms / 次调用** |
| 请求数 | 100,000 / 天 |
| KV 写入 | 1,000 次 / 天 |
| KV 读取 | 100,000 次 / 天 |
| KV 存储 | 1 GB（单值上限 25 MB） |
| 内存 | 128 MB |
| Cron Trigger | 5 个 / 账号 |

10ms 是硬约束。于是整个 Worker 被推倒重写：**不再「一次跑完」，而是「每次调用只做一个极小的单元任务」**。

### CPU 预算怎么压下来的

| 优化 | 效果 |
|---|---|
| 用 `indexOf` 切片代替 `matchAll` 全页正则扫描 | 单页解析 **3~12 ms → 0.1~0.23 ms** |
| cron 改为每分钟触发，每次只消费 1 个任务 | 单次调用 CPU 预算充足 |
| KV 按月份分片（`m:2026-09`） | 避免每次读写几百 KB 的大 blob |
| 看板改客户端渲染（Worker 只吐静态外壳） | 省掉服务端字符串拼接的 CPU |
| 用 `process.cpuUsage()` 在本地逐单元实测 | 证明列表任务 1~3 ms、详情任务 2~4 ms |

本地用 workerd 做过端到端验证：16 个栏目入队 → 连续 19 步详情任务 0 失败 → 第二轮扫描正确识别全部已抓取 → 看板渲染 8 组 42 条，搜索、月份过滤、NEW 标记都正常。

## 四、「有一个非常重要的内容，就是要下载页面里的文件」

这是用户强调的重点。第一版做出来的附件数永远是 **0**，查下来是个隐蔽的坑：

```python
# 错误写法
url.split('?')[0].endswith('.zip')
# 官网把文件名藏在 query 里：?fileUrl=xxx&fileName=%E5%85%AC%E7%A4%BA.zip
```

修正成 `looks_like_file()` 后，附件数从 **0 → 81**（分布在 59 条公告里）。同样的 bug 在 Worker 的 `looksLikeFile()` 里也有，一并修了。

顺带修的还有：`--dry-run` 跳过体积探测（逻辑写反了）、`--keyword` 不搜文件名、`human()` 对未知体积返回 0.0KB、`--resolve` 模式下 `sum()` 解析 `5.4` 报错、`sess` 变量作用域导致的 `NameError`。

实测下载过一个附件（`上尚电梯-环境影响登记表.pdf`，357,836 字节，`PDF document, version 1.7`），重跑能正确跳过。

## 五、OSS 直链的来龙去脉

用户直接丢过来一个 OSS 链接问能不能用。验证结论：**能用，但它不存在于任何页面里**。

```
网关  https://hbj.huzhou.gov.cn/api-gateway/jpaas-web-server/front/document/download?fileUrl=<密文>
  ↓ 302
中转  https://hbj.huzhou.gov.cn/cms_files/filemanager/1572864/attach/20269/9b8054a9….rar
  ↓ 301
OSS   https://zjjcmspublicnew.oss-cn-hangzhou-zwynet-d01-a.internet.cloud.zj.gov.cn/cms_files/…
```

用户贴的那个链接（湖州盛祥研磨，38.1 MB）实测：

- HTTP 200，`application/octet-stream`，`Content-Length: 39910780`
- 文件头 `Rar!\x1a\x07\x01\x00`
- **不需要 Referer，不需要鉴权**，0.2 秒响应

但 `fileUrl` 是服务端加密的，base64 解开是 128 字节密文，**算不出 OSS 路径**，只能跟随重定向。原始详情页 HTML 里也搜不到 `zjjcmspublicnew`。

于是给 `tools/download.py` 加了 `--resolve` 模式，用 `Range: bytes=0-0` 跟随重定向拿最终 URL 和体积，输出 `files/direct_links.csv`。已经跑完全部 81 个附件。

**附件规模结论**：81 个附件 ≈ **1 GB**，最大 137.5 MB，常见 20~40 MB。这直接否定了「让 Worker 下载附件」的方案——128 MB 内存、25 MB KV 单值、1 GB 命名空间，三个上限都会爆。分工定下来：**Worker 存元数据和链接，本体下载交给本地脚本**。

## 六、推到 GitHub：三步拦路虎

最后一步要把项目推到 GitHub，连续遇到三个问题：

**① DNS 被劫持。** 沙箱里 `github.com` 被解析到假的 `198.18.0.16`，TCP 通但 TLS 握手必挂（`SSL_ERROR_SYSCALL`）。解法是查出真实 IP 写进 `/etc/hosts`：

```
140.82.112.4   github.com
140.82.113.5   api.github.com
```

（`140.82.112.4` 这个 IP 对 `api.github.com` 是假的，会返回假的 301；但对 `github.com` 是真的。鉴定办法：请求 `https://api.github.com/zen`，真 GitHub 会返回一句格言，假的返回 301。）

**② 建不了仓库。** CodeBuddy 连接器给的令牌（`ghu_` 前缀，GitHub App user token）创建仓库时返回 `Resource not accessible by integration`。这一步只能由用户在网页上建。

**③ 推不上去。** 用户建好 `shengqiu/huzhou` 后，git 返回：

```
remote: Write access to repository not granted.
fatal: ... 403
```

用户尝试去 GitHub 给 App 授权这个仓库，但页面上**只有 codebuddy connector 一条，没有可选的仓库项**。于是做了一次无副作用的权限探针——对用户自己的另一个**公开**仓库 `claude-skills` 做 `git push --dry-run`：

```
remote: Permission to shengqiu/claude-skills.git denied to shengqiu.
```

令牌身份是用户本人，但**对任何仓库都没有 contents 写权限**。所以「临时改 Public」也救不了，不是可见性的问题，是权限位的问题。GitHub App 的授权页只能勾选 App **已经申请**的权限，而 CodeBuddy 这个 App 只申请了只读。

最终用用户临时生成的 classic PAT 推送成功，随后清理了本地令牌痕迹（`git remote set-url` 改回明文 https、没有 `.git-credentials`），并提示用户立即 revoke。

> **值得给 WorkBuddy 提的 bug**：连接器的 SKILL 文档写着支持 clone/push/创建 PR，但 App 只申请了 contents 只读权限，两者对不上。
